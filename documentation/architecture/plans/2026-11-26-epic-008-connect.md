# EPIC-008, cibles et connexion (US-008-01) — plan d'implémentation

> **Pour les agents :** sous-skill requis : superpowers:subagent-driven-development (recommandé) ou superpowers:executing-plans pour exécuter ce plan tâche par tâche. Les étapes utilisent des cases à cocher (`- [ ]`).

**Objectif :** le shell lit les cibles nommées de `kcc-targets.yaml`, s'y connecte avec `connect <cible>` (secret demandé sans écho ou lu dans l'environnement), affiche la cible dans le prompt, et peut s'y connecter au démarrage (`shell.target`).

**Architecture :** une cible est une valeur du domaine (`Target`) lue par un adaptateur de fichiers ; la connexion passe par un port (`KeycloakConnector`) implémenté dans `infrastructure.keycloak` par un **contexte Spring enfant par connexion**, construit avec les propriétés `keycloak.*` de la cible, qui crée son propre `KeycloakProvider` et pourra porter l'import à l'US-008-02. Le cas d'usage `ConnectTarget` relie les deux ; le shell garde la connexion courante dans sa session.

**Stack :** Java 25, Spring Boot 4.0.2, Spring Shell 4.0.4, SnakeYAML 2.5, Keycloak 26.5.3 (admin client), Testcontainers.

**Spec :** [ADR-010](../ADR-010-shell-mode-connecte.md) (« Des cibles nommées », « Une connexion ouverte à la demande », « Précisions »), [EPIC-008](../epics/EPIC-008-shell-connecte.md) (US-008-01), [ADR-005](../ADR-005-erreurs-et-codes-de-sortie.md).

Package racine : `io.github.doriangrelu.keycloak.config` (`...` ci-dessous).

## Contraintes globales

- Celles des plans précédents (licence, `spotless:apply`, ArchUnit : `infrastructure.cli.shell` ne voit ni `infrastructure.source` ni `infrastructure.keycloak`, `infrastructure.source` ne voit pas `infrastructure.keycloak` ; anglais pour le code et la doc utilisateur, français pour l'architecture ; aucune mention d'organisation ni de projet interne ; fins de ligne LF).
- Branche `feature/US-008-01-connect`. Commits au nom de `Dorian GRELU <doriangrelu839@gmail.com>`. Fin de story : `./mvnw -B verify` vert avec Docker (hors les 20 erreurs MockServer connues), sample vert, fusion, push sur les remotes du projet, « Réalisé » dans l'EPIC.
- L'import en ligne de commande (`run.operation=IMPORT`) et la normalisation gardent exactement leur comportement.
- Fichier des cibles : `<shell.root>/kcc-targets.yaml`. Champs d'une cible : `url` (obligatoire), `login-realm` (`master`), `client-id` (`admin-cli`), `grant-type` (`password` ou `client_credentials`, `password` par défaut), `user` (obligatoire pour `password`), `ssl-verify` (`true`), `connect-timeout` (`10s`). Un champ inconnu, une `url` absente ou un `grant-type` inconnu : le fichier est refusé avec un message qui nomme la cible et le champ.
- Secret : variable d'environnement `KCC_<CIBLE>_PASSWORD` (grant `password`) ou `KCC_<CIBLE>_SECRET` (`client_credentials`), nom de la cible en majuscules, `-` remplacé par `_` ; sinon demandé sans écho (`Password of '<user>'` ou `Secret of client '<client-id>'`). Jamais affiché, journalisé ni écrit.
- Codes de sortie (ADR-005) : cible inconnue ou fichier invalide → `2` ; Keycloak injoignable → `3` ; authentification refusée → `4`.
- Textes : `Connected to <cible> (<url>, Keycloak <version>)`, `Disconnected from <cible>`, `Not connected: use 'connect <target>'`, prompt `kcc[:<dossier>][@<cible>]>`.

## Points de revue

1. **Un mauvais mot de passe** donne le code `4` et un message clair, sans afficher le mot de passe ni une trace Java → tâches 2 et 4.
2. **Une URL injoignable** donne le code `3` en moins de `connect-timeout` (plus une marge), pas un blocage → tâches 2 et 4.
3. **Changer de cible** (`connect dev` puis `connect local`) ferme proprement la première connexion (contexte enfant fermé, aucun client HTTP laissé ouvert) → tâche 3.
4. **Le secret ne fuit jamais** : ni dans la sortie, ni dans les journaux, ni dans un message d'erreur, même en échec → tâches 2 et 4.
5. **L'import en ligne de commande** fonctionne exactement comme avant (aucun test existant modifié, `run.operation=IMPORT` inchangé) → tâche 2.
