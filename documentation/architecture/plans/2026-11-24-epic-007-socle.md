# EPIC-007, socle (US-007-01 à 03) — plan d'implémentation

> **Pour les agents :** sous-skill requis : superpowers:subagent-driven-development (recommandé) ou superpowers:executing-plans pour exécuter ce plan tâche par tâche. Les étapes utilisent des cases à cocher (`- [ ]`).

**Objectif :** un shell Spring Shell lancé par `run.operation=SHELL`, qui lit le dossier d'un realm (JSON ou YAML, placeholders conservés) et sait réécrire ses fichiers sans les abîmer, avec `realm format`.

**Architecture :** les commandes Spring Shell (`infrastructure.cli.shell`) appellent des cas d'usage (`application.definition`) qui travaillent sur un modèle de définition (`domain.definition`) ; les questions passent par le port `Questions`, les fichiers par le port `RealmDefinitions`, implémenté dans `infrastructure.source.definition` sur une abstraction d'arbre commune à SnakeYAML (avec commentaires) et à Jackson.

**Stack :** Java 25, Spring Boot 4.0.2, Spring Shell 4.0.4 (cœur seul, sans JLine), SnakeYAML 2.5 et Jackson 2.20 (déjà présents), JUnit 5, AssertJ, ArchUnit.

**Spec :** [ADR-008](../ADR-008-shell-edition-des-definitions.md), [EPIC-007](../epics/EPIC-007-shell-edition.md). Les plans des stories suivantes (04 à 11) viendront après ce socle ; la US-007-06 commence par la conception du formalisme des règles avec l'utilisateur.

## Contraintes globales

- Paquet racine : `io.github.doriangrelu.keycloak.config`. Chaque nouveau fichier Java porte l'en-tête de licence du projet (celui des fichiers existants) ; `./mvnw -B -q spotless:apply` avant chaque commit.
- Spring Shell : `org.springframework.shell:spring-shell-starter:4.0.4` et, en test, `org.springframework.shell:spring-shell-test:4.0.4`. Pas de module JLine.
- Le domaine reste en Java pur ; l'application ne voit ni Spring Boot ni Jackson ni SnakeYAML (seulement `org.springframework.stereotype`) ; `infrastructure.source` ne dépend ni du SDK Keycloak ni de `infrastructure.keycloak` (règles ArchUnit existantes).
- Les placeholders sont conservés tels quels (`{{appUrl}}`, `{{appUrl:https://localhost}}`, `{{env}}-mon-realm`) ; le shell écrit toute valeur qui en contient en chaîne entre guillemets doubles.
- Numérotation des fichiers : `00-realm`, `20-clients`, `30-roles`, `40-groups` ; extension `.yaml` ou `.json`.
- Correspondance type d'application ↔ flows : tableau de l'ADR-008 (clés `publicClient`, `standardFlowEnabled`, `implicitFlowEnabled`, `directAccessGrantsEnabled`, `serviceAccountsEnabled`) ; `bearerOnly` n'est jamais écrit.
- Code et doc utilisateur en anglais ; documentation d'architecture en français ; aucune mention d'organisation interne.
- Une branche par story ; un commit par tâche (`git -c user.name="Dorian GRELU" -c user.email="doriangrelu839@gmail.com" commit`, message terminé par `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`) ; en fin de story : `./mvnw -B verify` vert (hors les 20 erreurs MockServer connues sous Windows), fusion rapide dans `main`, push sur `origin` et `adsn`, section « Réalisé » de la story dans l'EPIC-007.

## Points de revue

Ce que la spec implique sans qu'une tâche le dise, et qui piégerait un utilisateur :

1. **Un import ou une normalisation ne doit jamais ouvrir de shell** (une CI resterait bloquée sur l'entrée standard) → test de la tâche 1.
2. **En mode script, une question sans réponse échoue (code `2`, question nommée) au lieu d'attendre une saisie** → test de la tâche 2.
3. **Un placeholder survit à la lecture puis à la réécriture**, y compris dans une valeur composée et en JSON ; un fichier au placeholder non quoté met le realm en lecture seule → tests des tâches 4, 5 et 7.
4. **Modifier un client écrit à la main garde les clés que le modèle ne gère pas** (`protocolMappers`, un attribut inconnu, un commentaire) → test de la tâche 7.
5. **Les fins de ligne et l'encodage d'un fichier sont respectés** : un fichier en CRLF reste en CRLF, un accent dans une description reste intact (UTF-8) → test de la tâche 6.
